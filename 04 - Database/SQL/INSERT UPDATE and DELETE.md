# INSERT UPDATE and DELETE

%% Graduated via [[Refiner Spec (Graduate)]] using SQL/_refiner.md. Worked example omitted — already worked through in pgAdmin. Graduated as ONE note because all three share a single load-bearing idea: the WHERE clause is the only thing standing between you and every row in the table. %%

## Retrieval Prompts

1. The one that matters most: what do `UPDATE "students" SET "studentPhone" = NULL;` and `DELETE FROM "students";` have in common?
> [!answer]- reveal
> **Neither has a `WHERE`, so both hit every row in the table** — and both are perfectly valid SQL that runs without warning. This is the single most destructive mistake in the language, and it looks identical to a correct statement right up until you press execute.
>
> The habit that prevents it: **write the `SELECT` first.** Compose `SELECT * FROM "students" WHERE …`, confirm the row set is exactly what you intend, *then* swap `SELECT *` for `UPDATE … SET` or `DELETE`. In a real database, wrap it: `BEGIN;` → run it → check the row count → `COMMIT;` or `ROLLBACK;`.

2. When may you omit the column list in an `INSERT`, and why is doing so discouraged?
> [!answer]- reveal
> Only when you supply a value for **every** column, in **exact table order**. It's discouraged because it's positional: adding, dropping, or reordering a column silently changes which value lands where, and nothing errors as long as the types still line up. Naming columns makes the statement self-documenting and order-independent.

3. Postgres replies `INSERT 0 1`. What are those two numbers?
> [!answer]- reveal
> The first is an **OID** — legacy, and always `0` in modern Postgres. The second is the **number of rows inserted**. So `INSERT 0 1` = one row in. A multi-row `VALUES (…), (…), (…)` returns `INSERT 0 3`.

4. ⚠ Predict: your `courses` table has `"courseId" INT GENERATED ALWAYS AS IDENTITY`. What happens when you run `INSERT INTO "courses" ("courseId", "courseName") VALUES (1, 'Web Development');`?
> [!answer]- reveal
> It **fails**: `ERROR: cannot insert a non-DEFAULT value into column "courseId"` / `HINT: Use OVERRIDING SYSTEM VALUE to override.`
>
> `GENERATED ALWAYS` means the database owns that column absolutely. The fix is to **omit it** — `INSERT INTO "courses" ("courseName") VALUES ('Web Development');` — and let the identity supply it. (`GENERATED BY DEFAULT AS IDENTITY` would have accepted your value.) **This exact statement appears in your slides as a worked example; it cannot run.**

5. You just inserted a row and need its generated key. What's the Postgres way, and what's the naive way you should avoid?
> [!answer]- reveal
> **`RETURNING`**: `INSERT INTO "courses" ("courseName") VALUES ('Quantum Computing') RETURNING "courseId";` — one round trip, atomic, no race.
>
> The naive way is a follow-up `SELECT MAX("courseId")`, which is wrong under concurrency: another session's insert can land in between and you retrieve their key. `RETURNING` also works on `UPDATE` and `DELETE`, which makes it excellent for auditing exactly which rows a statement touched.

6. You try to delete a `courses` row that a `students` row references, with the FK declared `ON DELETE NO ACTION`. What happens — and where would you go to change that behaviour?
> [!answer]- reveal
> The delete is **rejected** with a foreign-key violation; Postgres won't orphan the child. Changing it means altering the **FK's referential action** (`CASCADE`, `SET NULL`, …) — a schema change, not something you can override at statement level. See [[Keys Primary and Foreign]].

7. Interleaving — you need to empty a table completely. Which of `DELETE`, `TRUNCATE`, `DROP` do you reach for, and what decides it?
> [!answer]- reveal
> **`DELETE FROM t;`** if row triggers must fire or you might want to filter. **`TRUNCATE t;`** to wipe it fast and optionally `RESTART IDENTITY`. **`DROP TABLE t;`** if the table itself should stop existing. Full comparison in [[CREATE TABLE and Constraints]].

## Rebuild Drill

From a blank query tool, against `courses` / `students`, perform a complete safe-modification cycle from memory:

1. `INSERT` a new course **without** specifying its identity column, using `RETURNING` to capture the new id.
2. `INSERT` three students in a **single** statement, all referencing that new course.
3. `UPDATE` exactly one of them — but write and run the `SELECT` form first to prove your `WHERE` targets one row.
4. `DELETE` exactly one of them, again `SELECT`-first.
5. Attempt to `DELETE` the course itself.

**Success criteria:** step 1 returns the generated id without you typing it. Step 2 reports `INSERT 0 3`. Steps 3 and 4 report `UPDATE 1` / `DELETE 1` — if either reports a larger number, your `WHERE` was wrong and that's the lesson. Step 5 is **rejected** with a foreign-key violation, and you can name the constraint that blocked it.

## Flashcards

#flashcards/sql/dml

What is the practical habit that prevents an unqualified UPDATE or DELETE?
?
Write and run the SELECT with that WHERE first, confirm the row set, then swap in UPDATE/DELETE. Or wrap in BEGIN, check the row count, then COMMIT or ROLLBACK.

In the reply INSERT 0 1, what are the two numbers?
?
A legacy OID (always 0 in modern Postgres) and the number of rows inserted.

Why does inserting an explicit value into a GENERATED ALWAYS AS IDENTITY column fail?
?
The database owns that column: "cannot insert a non-DEFAULT value". Omit the column, or write OVERRIDING SYSTEM VALUE. GENERATED BY DEFAULT would have allowed it.

How do you get the key generated by an INSERT, and why not SELECT MAX(id)?
?
Use RETURNING — one round trip and race-free. SELECT MAX(id) can return another concurrent session's key.

Why is an INSERT without a column list discouraged even though it's valid?
?
It's positional. Adding, dropping or reordering a column silently changes which value lands where, with no error while the types still line up.
