# JPA and Its Annotations

%% Graduated via [[Refiner Spec (Graduate)]] using Spring/_refiner.md. This is a study/test surface, not a reference to reread. Attempt every prompt closed-book BEFORE expanding an answer. %%

## Worked Example

A minimal entity — the annotations are the whole point, so read each subgoal:

```java
import jakarta.persistence.*;

// 1. Mark this plain class as a JPA-managed entity and bind it to a table
@Entity
@Table(name = "students")
public class Student {

    // 2. Declare the primary key and hand key generation to the database
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "student_id")
    private int id;

    // 3. Map a field to a column whose name differs from the field
    @Column(name = "student_name")
    private String name;

    // 4. Deliberately keep a field OUT of the database
    @Transient
    private int sessionScratch;

    // JPA needs a no-arg constructor; it exists by default since none other is declared.
}
```

**Explain in plain English (EiPE):** This class tells the ORM to store each `Student` object as a row in the `students` table — `id` is filled in by the database, `name` maps to a differently-named column, and `sessionScratch` is intentionally never saved.

## Retrieval Prompts

%% Answer OUT LOUD or on paper first. Only then expand. %%

1. Why annotate a class with `@Entity` at all, instead of just writing `CREATE TABLE` + `INSERT` SQL yourself?
> [!answer]- reveal
> `@Entity` marks the class as a persistence-managed type, so the ORM maps each instance to a row and **generates the CRUD SQL for you** — removing the JDBC boilerplate and the object↔table conversion you'd otherwise hand-write.

2. `@Table` vs `@Column` — what does each map, and when do you actually *need* to write them?
> [!answer]- reveal
> `@Table` maps the **class → a table**; `@Column` maps a **field → a column**. You only need them when the DB name/config differs from the default (default = the class/field name), or to set constraints like `nullable`/`length`/`unique`.

3. `@GeneratedValue` — why let the database assign the primary key rather than setting `id` yourself in Java?
> [!answer]- reveal
> The database **owns key generation** (identity column / sequence). Letting it assign avoids collisions and race conditions that manual assignment can't safely prevent across concurrent inserts.

4. How is JPA's `@Transient` different from Java's built-in `transient` keyword?
> [!answer]- reveal
> Different subsystems: `@Transient` excludes a field from **database persistence**; the `transient` keyword excludes a field from **Java serialization**. One is about the ORM, the other about `ObjectOutputStream`.

5. When would you reach for `@Version`, and what does it *do*?
> [!answer]- reveal
> For **optimistic locking**. JPA checks the version column on update; if another transaction changed the row first, the update fails instead of silently overwriting — detecting the concurrent modification.

## Correctness Check

Ran `Spring/_refiner.md` checklist + verified every annotation claim (spec step ④):

- ✅ **Package** — `jakarta.persistence.*` is correct for Spring Boot 3+ (was `javax.persistence` pre‑Boot 3).
- ✅ **No-arg constructor** — JPA requires one; present by default here since no other constructor is declared.
- ✅ **Architecture cardinalities** — EMF→EM (1:N) and EM→EntityTransaction (1:1) verified against the JPA model.
- ⚠️ **Fixed from raw notes:** the source says `@Entity` "can be applied to a Class or an Interface of Enums." That's wrong — **`@Entity` goes on a concrete class** (an entity can't be an interface or an enum). Corrected in the worked example.
- ⚠️ **Fixed from raw notes:** the source's `@GeneratedValue(strategy=SEQUENCE, generator="ID_SEQ")` is incomplete — a `generator` name requires a matching **`@SequenceGenerator(name="ID_SEQ", ...)`** or it won't resolve, and the enum is `GenerationType.SEQUENCE`. I used `IDENTITY` in the example to keep it self-contained.
- ⚠️ **Spot-check (<90%):** the source's `@Version private Date version;` is dubious — the JPA spec lists `@Version` types as `int/Integer`, `short/Short`, `long/Long`, `java.sql.Timestamp`. **`java.util.Date` is not a spec-listed version type**; prefer an integer version or `Timestamp`. Verify against your Hibernate version before trusting it.
- ➖ **N/A this note:** bean-scope / DI / `@Transactional` checklist items don't apply here (no beans or injection in a pure entity) — noted so it's clear they were considered.
